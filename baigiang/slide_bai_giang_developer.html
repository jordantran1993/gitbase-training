🌿 GIT THỰC CHIẾN CHUYÊN SÂU

Hiểu Thấu Bản Chất: git merge vs git rebase

Bóc tách cơ chế bên dưới nắp ca-pô và quy chuẩn thông điệp Conventional Commits quốc tế.

CƠ CHẾ 1: git merge (3-Way Merge) Bắc cầu nối 2 cành
main: A ─── B ─── C ─────────────── M (Merge Commit)
                      \ /
feature:                 D ─────────── E
  • 🔸 Cơ chế ngầm: Git tìm commit gốc chung, tạo ra Merge Commit (M) có 2 cha (C & E).
  • 🔸 Hệ quả: Lịch sử phân nhánh rối rắm như mạng nhện (diamond graph) khi nhiều người cùng làm.
  • 🔸 Ưu điểm: Giữ nguyên chính xác mốc thời gian diễn ra của từng nhánh.
CƠ CHẾ 2: git rebase (Re-Basing) Bứng cây trồng lên đỉnh đồi
main: A ─── B ─── C
                      \
feature:                 D' ─── E' (Hash mới, thẳng tắp!)
  • 🔹 Cơ chế ngầm: Gỡ D, E thành patch tạm, tua về C, áp D', E' lên trên đỉnh.
  • 🔹 Bản chất: Mỗi commit sinh ra có mã SHA-1 Hash hoàn toàn mới. Lịch sử thẳng tắp (Linear History).
  • 🔹 Ưu điểm: Không có commit rác, lịch sử cực sạch, dễ dàng dùng git bisect để truy vết bug.
⚠️ QUY TẮC VÀNG CỦA REBASE (THE GOLDEN RULE)

✔ ĐƯỢC: Rebase trên nhánh riêng (feature/*) trước khi tạo PR để cập nhật code mới.
❌ CẤM KỴ: Tuyệt đối không rebase trên nhánh chung (main, develop) vì làm thay đổi lịch sử cả team!

📝 Chuẩn Quốc Tế: Conventional Commits Tra cứu chuẩn ➔
feat: tính năng fix: sửa lỗi refactor: sửa code docs: tài liệu chore: config
🌿 SO SÁNH TRỰC QUAN BEFORE & AFTER

Soi Tận Mắt Cây Commit: Trước & Sau Khi Merge vs Rebase

Quan sát sự dịch chuyển của các commit, nhánh và mã SHA-1 Hash trong từng trường hợp.

01. BAN ĐẦU (BEFORE)

Cùng xuất phát từ C. main có thêm D, feature có thêm X, Y:

main: A ── B ── C ── D
                     \
feature:             X ── Y
• Gốc chung ban đầu: C
• Feature tụt lại sau đỉnh D của main
02. SAU KHI MERGE

Chạy git merge feature trên nhánh main:

main: A ── B ── C ── D ──── M
                     \ /
feature:             X ─────── Y
• Sinh commit gộp M (2 cha D & Y)
• Hash của X, Y giữ nguyên 100%
• Cây rẽ nhánh tạo hình mạng nhện
03. SAU KHI REBASE

Chạy git rebase main trên nhánh feature:

main: A ── B ── C ── D
                             \
feature:                    X' ── Y'
• Không có commit rác M
• X', Y' mang mã SHA-1 Hash MỚI
• Lịch sử nối tiếp thẳng tắp 1 hàng
Tiêu Chí So Sánh git merge git rebase
Mã Hash Commit GIỮ NGUYÊN (X và Y không đổi SHA-1) BỊ THAY ĐỔI HOÀN TOÀN (X, Y biến thành X', Y' với hash mới)
Hình dạng cây Git (git log) Phân nhánh rườm rà (Non-linear, đan xen như mạng nhện) Thẳng tắp 1 đường duy nhất (Linear History, cực kỳ sạch sẽ)
Khả năng tìm bug (git bisect) Khó hơn vì có các commit gộp rác xen ngang Rất dễ dàng và tự động, cô lập đúng commit gây lỗi trong tích tắc

Kỹ Thuật Cứu Nguy: git stash & git cherry-pick

Hai tuyệt chiêu xử lý các tình huống đột xuất trong dự án hàng ngày.

TÌNH HUỐNG 1

Sếp Giao Việc Gấp Giữa Chừng

Đang code dở tính năng Đăng nhập (50 dòng code lỗi chưa thể commit). Tech Lead yêu cầu checkout sang nhánh hotfix gấp!

# 1. Cất toàn bộ code dở vào tủ khóa
git stash -u

# Thư mục sạch tinh, checkout đi sửa hotfix...
git checkout hotfix/banner-overflow

# 2. Xong việc, quay lại lấy code ra làm tiếp
git checkout feature/login
git stash pop
TÌNH HUỐNG 2

Nhặt Đúng 1 Hạt Ngọc Giữa Bãi Rác

Đồng nghiệp ở nhánh khác có viết 1 hàm tính thuế rất hay (mã commit a1b2c3d). Nhưng cả nhánh của họ còn đang lỗi dở dang.

# Tuyệt đối KHÔNG merge cả nhánh của họ
# Đứng ở nhánh của mình và bốc đúng 1 commit:
git cherry-pick a1b2c3d

✔ Git chỉ lấy đúng duy nhất commit đó đập vào nhánh của em!

Làm Chủ git reset: Phân Biệt Soft, Mixed & Hard

Hiểu thấu đáo 3 trạng thái bộ nhớ để quay ngược lịch sử an toàn.

Lệnh Reset (Lùi 1 commit) Working Directory (File ổ cứng) Staging Area (Sau git add) Tình Huống Sử Dụng Thực Tế
git reset --soft HEAD~1 GIỮ NGUYÊN GIỮ NGUYÊN (Staged) Lỡ tay commit nhầm file .env mật khẩu, hoặc muốn đổi lại commit message cho chuẩn. Rất an toàn!
git reset --mixed HEAD~1
(Mặc định khi chỉ gõ git reset)		 GIỮ NGUYÊN BỊ HỦY (Unstaged) Lỡ git add . cả đống file lộn xộn, muốn đưa về trạng thái màu đỏ để chia nhỏ ra commit lại từng phần.
git reset --hard HEAD~1 XÓA SẠCH SẼ XÓA SẠCH SẼ NÚT TỰ HỦY: Thử nghiệm tính năng mới thất bại nát bét, muốn xóa trắng quay về quá khứ. Cực kỳ cẩn thận!
💡 Tuyệt chiêu xem lịch sử siêu gọn gàng: git log --oneline --graph --all

Biến terminal thành một bản đồ cây commit trực quan, nhìn rõ ai đang rẽ nhánh nào trong 5 giây mà không bị tràn màn hình.

🐧 HỆ ĐIỀU HÀNH MÁY CHỦ

Tại Sao Developer Nhất Định Phải Học Thêm Ubuntu?

95% máy chủ trên Internet chạy Linux. Kỹ năng vận hành sản phẩm thực tế bắt đầu từ đây.

Thực Tế Khác Biệt Giữa Máy Cá Nhân & Server

  • 🖥️ Máy cá nhân (Local): Dùng chuột, giao diện đẹp (Windows / macOS), bấm nút Run là chạy.
  • ☁️ Máy chủ (Production / Staging): Hoàn toàn không có giao diện đồ họa (No GUI). 100% thao tác điều khiển thông qua màn hình dòng lệnh (Terminal / SSH).
  • 🐳 Hệ sinh thái Docker & Cloud: Hầu hết container Docker và dịch vụ đám mây (AWS, GCP, DigitalOcean) đều tối ưu trên nhân Linux Ubuntu.

4 Kỹ Năng Sống Còn Khi Đụng Vào Ubuntu

1. Quản lý tiến trình & Dịch vụ

Khởi động lại Nginx, PHP-FPM, MySQL khi server bị treo (systemctl restart nginx).

2. Phân quyền file (chmod / chown)

Fix lỗi kinh điển "Permission Denied" khi deploy code lên server mà thư mục cache không ghi được.

3. Soi Log sự cố thời gian thực

Dùng lệnh tail -f /var/log/nginx/error.log để bắt đúng lỗi lúc web bị sập giữa đêm.

4. Tự động hóa với Cronjob

Lên lịch tự động chạy gửi email, quét đơn hàng, sao lưu database mỗi ngày.

💡 Lời khuyên cho Intern: Không cần thành chuyên gia Linux ngay, nhưng hãy tập làm quen với Terminal, dùng WSL2 (Windows Subsystem for Linux) hoặc cài Ubuntu trong Docker để không bị bỡ ngỡ khi ra dự án thật.

MySQL Transactions: Cơ Chế Sống Còn Bảo Vệ Dữ Liệu

Hiểu thấu bản chất START TRANSACTION, COMMIT và ROLLBACK qua bài toán ngân hàng.

THẢM HỌA: KHÔNG DÙNG TRANSACTION

Bài toán: Khách A chuyển 1.000.000đ cho Khách B

-- Lệnh 1: Trừ tiền tài khoản A (Thành công)
UPDATE accounts SET balance = balance - 1000000 WHERE id = 'A';

⚡ SỰ CỐ: Cúp điện / Đứt mạng / Server crash!

-- Lệnh 2: Cộng tiền B CHƯA KỊP CHẠY!
UPDATE accounts SET balance = balance + 1000000 WHERE id = 'B';
💥 Hậu quả: A bị trừ tiền nhưng B không nhận được. Tiền biến mất, sai lệch kế toán, khách hàng kiện cáo!
GIẢI PHÁP: BỌC TRONG TRANSACTION

Nguyên lý All or Nothing (Hoặc tất cả thành công, hoặc hủy hết):

START TRANSACTION; -- 1. Mở chiếc hộp an toàn

UPDATE accounts SET balance = balance - 1000000 WHERE id = 'A';
UPDATE accounts SET balance = balance + 1000000 WHERE id = 'B';

-- Nếu CẢ HAI lệnh đều chạy trơn tru:
COMMIT; -- 2. Ghi nhận vĩnh viễn vào ổ đĩa

-- Nếu CÓ BẤT KỲ LỖI GÌ xảy ra ở giữa:
ROLLBACK; -- 3. Hoàn tác sạch, tiền A vẫn còn nguyên!
1. START TRANSACTION

Tắt chế độ tự động lưu (autocommit). Toàn bộ các thay đổi chỉ ghi tạm vào bộ nhớ RAM.

2. COMMIT

Xác nhận phiên giao dịch thành công mỹ mãn. Ghi dữ liệu chính thức xuống ổ đĩa cứng.

3. ROLLBACK

Phao cứu sinh khi gặp lỗi: Hủy toàn bộ thao tác dở dang, đưa DB về đúng trạng thái ban đầu.

Làm Chủ PHP & Laravel: Nền Tảng & Request Lifecycle

Tập trung vào nền móng vững chắc và hiểu thấu vòng đời để giải quyết mọi bài toán thực tế.

1. Nền Móng PHP Base (Bắt Buộc Chắc)

  • 🔹 OOP Hiện Đại: Hiểu rõ Interface (hợp đồng cam kết), Abstract Class, Trait (tái sử dụng code) và Dependency Injection (tiêm phụ thuộc).
  • 🔹 PHP 8+ Strict Types: Luôn khai báo kiểu dữ liệu rõ ràng cho tham số và giá trị trả về (Type Hinting & Return Type) để code an toàn, không bị lỗi ngầm.
  • 🔹 Exception Handling: Tư duy bắt và xử lý ngoại lệ bài bản bằng try - catch - finally thay vì để ứng dụng nổ tung văng lỗi trắng trang.

2. Vòng Đời Request Trong Laravel (Trục Xương Sống)

Hiểu luồng đi 6 bước của 1 request để bắt đúng bệnh:

1. public/index.php ➔ Điểm đón request đầu tiên
2. HTTP Kernel ➔ Khởi động hệ thống (Boots)
3. Service Providers ➔ Đăng ký dịch vụ (Register & Boot)
4. Routing & Middleware ➔ Lọc bảo mật (Auth, CORS, RateLimit)
5. Controller & FormRequest ➔ Validate & Xử lý logic nghiệp vụ
6. HTTP Response ➔ Trả JSON hoặc View HTML về client

OOP Thực Chiến: 4 Tính Chất Cốt Lõi Qua Ví Dụ Web

Thoát khỏi lý thuyết "Chó & Mèo" giáo điều, hiểu bản chất 4 tính chất qua nghiệp vụ thực tế.

1. Tính Đóng Gói & 2. Tính Kế Thừa

1. Tính Đóng Gói (Encapsulation)

Giấu dữ liệu nhạy cảm. Thuộc tính $password, $balance để private. Muốn sửa phải qua hàm changePassword() hoặc withdraw(), cấm tự tiện sửa $user->balance = 999999999.

2. Tính Kế Thừa (Inheritance)

Tái sử dụng code thông minh. Class cha User có name, email. Các class con Admin và Customer kế thừa lại toàn bộ, chỉ viết thêm quyền hạn riêng.

3. Tính Đa Hình & 4. Tính Trừu Tượng

3. Tính Đa Hình (Polymorphism)

Cùng 1 tên hàm nhưng xử lý khác nhau. Gọi $payment->pay(): Cổng VNPay thì quét QR, cổng COD thì in phiếu thu tiền mặt. Không cần viết 10 cái if/else!

4. Tính Trừu Tượng (Abstraction)

Giấu kín sự phức tạp bên dưới. Gọi hàm sendNotification() là thông báo bay đi, không cần bận tâm bên dưới nó kết nối cổng mạng hay mã hóa thế nào.

💡 Tư duy đi làm: Trường học dạy OOP để thi cử; Doanh nghiệp dùng OOP để khi yêu cầu thay đổi, chỉ cần viết thêm Class mới chứ không đập phá code cũ!

Cookie & Session: Bản Chất Dễ Hiểu Qua 2 Ví Dụ Đời Thực

Giải mã cách máy chủ nhận diện và ghi nhớ thông tin người dùng trên giao thức Stateless HTTP.

2 Ví Dụ Đời Thường Gặp Hàng Ngày

🛒 Ví dụ 1: Giỏ Hàng Mua Sắm (Cookie)

Chưa đăng nhập nhưng bấm thêm 2 cái áo. Cookie trên trình duyệt lưu mã giỏ hàng. Tắt máy đi ngủ, hôm sau mở lại 2 cái áo vẫn còn nguyên!

🔑 Ví dụ 2: Ghi Nhớ Đăng Nhập (Session + Cookie)

Đăng nhập thành công, Server tạo Session lưu thông tin. Trình duyệt nhận Cookie chứa session_id. Lần sau mở tab mới tự vào thẳng, không cần gõ lại mật khẩu.

Mô Hình Tủ Đồ & 3 Cờ Bảo Mật Cookie

📦 Session: Tủ đồ an toàn ở máy chủ (Server).
🎫 Cookie: Thẻ số chìa khóa nhét túi quần (Trình duyệt).

1. HttpOnly Cấm JavaScript đọc Cookie, chặn đứng hacker chôm tài khoản qua XSS.
2. Secure Chỉ gửi qua HTTPS an toàn, chống nghe lén Wi-Fi công cộng.
3. SameSite Chống web lừa đảo bên ngoài gửi trộm request (chống CSRF).
